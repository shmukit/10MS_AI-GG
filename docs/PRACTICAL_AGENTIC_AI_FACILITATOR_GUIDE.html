Why this order (read once before you teach)

What participants should be able to do by the end of the day

By the end of the live workshop, each participant (or small team) should be able to:

  1. Point to one real work process they chose today (not five ideas).
  2. Show that process running once on their screen: something starts it → AI does a clear step → a result appears in a real place (Sheet, Doc, email draft, chat) → a human still approves anything external or high-risk.
  3. Explain, in plain language, what the AI is allowed to do, what it must never do alone, and how they check the output.
  4. Re-run that path without you standing next to them, and name one habit they will keep for the next 30 days.

Everything earlier in the day exists so that final run is the right process, with clear instructions, and safe enough for Monday—not so they collect tools or theory.

How the day builds (full sentences)

The day has five layers. Each layer adds something the next layer needs.

Session 0 — Set up the room and the coach.
Participants open their tools, create one Teacher Project, and start one chat they will keep all day. They also learn three plain words (chat, assistant, agent) so later activities have shared language. Without this, every later step becomes a login problem or a new empty chat with no memory.

Session 1 — Use AI as a daily helper, then commit to one job.
They write a short brief, hire a Work Assistant, run it three times, and take one round of feedback. Only after they have felt what good and bad AI output looks like do they lock one work process for the rest of the day. Then they pick at most three tools and ground AI in real documents for that process only.
Reason: if they shop for tools before locking a job, the afternoon becomes tourism. If they lock a job before feeling AI, they lock from fear or FOMO.

Session 2 — Turn that job into a reusable path.
They choose how much structure the job needs, map the steps, write operating rules (ETCSLV—especially Limits and Validation), and lock a build pattern. Then they write standing instructions (the brain) and make a simple automation or semi-automatic path (the hands) run once.
Reason: instructions without a run are notes; a run without instructions is fragile. Brain comes before hands.

Session 3 — Manage the path that already runs.
They name the smallest set of AI jobs for that same path, rewrite the operating rules as a Monday-ready checklist (same ETCSLV letters—not a new framework), break the path on purpose, fix it, re-run it alone, demonstrate it, and write a short 30-day habit plan.
Reason: “managing AI” is credible only after something actually moves. Session 3 does not start a second product.

Session 4 — Optional reading later.
Deeper articles and a short video for after the workshop. Not required live.

What the three session names mean

  • Work WITH AI: You use AI beside you (an assistant with standing instructions).
  • Work THROUGH AI: The job moves along a path (clear instructions + a run you can show).
  • Work BY AI: You manage that path (who does what, what is allowed, what breaks, what you re-run on Monday). You do not start a second project.

Why not a different order?

Tempting reorder Why we don’t
Lock a process at 0.3 before any assistant They would commit before they have felt good vs bad AI output. Tasks 1.1–1.3 build taste; 1.4 commits.
Browse many tools before locking a process They try eight apps and finish nothing. Always lock → tools → files.
Build n8n/automation before map and Limits/Validation Demos look clever and fail on Monday. Specify, then run.
Design a multi-agent org chart before anything runs Looks impressive; usually fiction. Run a thin path first (2.6), then name only the jobs that path needs (3.1).
Write the full rules checklist / roles before 2.6 Sounds more “agentic” on paper; weaker in a one-day room. Managing is believable after something runs.
Demo Day without Failure Lab False confidence. Break on purpose before the audience.

Where this order is strong vs weak (be honest in the room)

Keep these choices
1. Feel AI → lock one job → then pick tools (1.1–1.6).
2. Standing instructions (2.5) before automation (2.6).
3. A path that runs (2.6) before “manager of AI work” (3.x).
4. One Teacher chat all day—more important than any framework name.

Watch these weak joints live
1. 0.4 “agent” is mostly vocabulary. Say: “You will earn this word this afternoon.”
2. The Work Assistant from 1.2 may not match the process locked at 1.4. At 2.5, force a choice: extend that Work Assistant or create one new Project for the locked job—not both.
3. 1.5 (tools) is long. If late, cut your tool-tour talking—not 1.4, 2.6, 3.4, or 3.5.
4. 3.1 (AI jobs) becomes theater if their path is only three steps. Cap at two or three jobs for this path.
5. 3.2 is the same ETCSLV rules, written so a colleague could follow them on Monday—not a new framework. Say that out loud.
6. A template in 2.6 may use sample data. That is fine if the shape matches their job (start → AI → result → human check). Do not promise a live Meta-to-CRM build in the room.
7. Success is often a simple running path plus clear instructions—not a multi-agent empire by 5pm. Treat that as a win.

When someone is lost, ask only these four questions

“What process did you lock? Where are the standing instructions? Can you run it once on screen? What must a human still approve?”

If they cannot answer, do not add more roles, tools, or dashboards.

1. What this workshop is

Who is in the room: Working professionals — managers, HR, marketing, analysts, founders, operations, consultants, educators. They are not software engineers.

What the day is about: People learn to manage AI the way they manage junior employees: give clear instructions, check the work, set limits, and only automate what is safe.

The story of the day (say this once at the start):

  1. Work WITH AI — Use AI as a daily helper (better prompts, right tool, memory).
  2. Work THROUGH AI — Turn one messy work process into a reusable assistant and a path that can run.
  3. Work BY AI — Treat AI like a small team: roles, rules, failure tests, then ship.

What “done” means at the end of the day:
Each person (or small team) can live-demonstrate one real work process that runs like this:

Something starts the work (a form, an email, a checklist, a pasted note) → AI does a clear step → the result appears where work actually goes (Google Doc, Sheet, email draft, Slack, Slides, etc.) → a human still approves anything external or high-risk.

That running path is the product. Notes alone are not enough.

You are the Workshop Teacher Agent for “Practical Agentic AI for Productivity.”

T Tools — interact with external systems?
C Context — what must AI always know?
S State — what must persist beyond one chat?

V Validation — how do we know it’s correct?

Appendix C — Do / don’t

Do

  • Keep one Teacher chat all day (“use earlier context”).
  • Demo short; rescue long.
  • Force slices that can re-run today.
  • Require a live run.
  • After every AI reply: Stop → Read → Decide.
  • Allow optional paper/blank note for thinking — not as a paste source.

Don’t

  • Add Miro/Mural or a Google Slides Working Pack.
  • Require multi-block pastes (process + map + ETCSLV) in one prompt.
  • Hop Teacher ↔ Work Assistant except the one feedback round (1.3).
  • Let people try more than 3 tools for today’s locked process.
  • Accept a deck as capstone without a run.
  • Introduce ETCSLV only via a Teacher prompt with no explanation.
